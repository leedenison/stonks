## Scope

One admin page lists what needs an administrator, across every surface, and is the
admin home. The page derives an alert when it reads rows that already exist. The alert
disappears when an administrator settles its cause. Each alert carries the action that
settles it.

The kinds:

- A failed or interrupted run.
- An open block.
- A ticker that names nothing: keys with transactions state the ticker, and it names
  nothing on every day.
- A ticker validity gap: part of a ticker's transaction period lies outside every
  confirmed interval.
- An unhandled corporate action that an administrator has not decided.
- A finding that records a choice the system made between sources, and a split a
  statement states that the calendar lacks.

The alerts page carries the system run actions as a card beside the alerts. The action
bar of a page holds the page's own actions; a catalogue of operations is a table in the
body.

An administrator decides whether a corporate action restates shares, from the alert and
from a corporate actions tab on the instrument. See
[003-decide-corp-act-restates-shares.md](003-decide-corp-act-restates-shares.md).

A broker description awaiting verification is shown as a section labelled as a mock,
with static rows that carry nothing to act on, so the page's shape accounts for it.

## Open questions

Each carries the answer proposed at opening.

- Which findings are alerts. Proposed: the kinds that record a choice: contradiction,
  identifier disagreement, broken ticker validity bracket, missed event and unmatched
  split. Dropped and merged stay on the run page. The open block is the alert, rather
  than the finding that reports it. An unhandled corporate action is its own kind,
  rather than a finding alert.
- Whether an administrator can dismiss an alert. Proposed: a finding alert is open
  while its finding is uncleared, and clearing it is the acknowledgement. When an
  administrator clears an occurrence on one run, it returns when a later run raises it
  again. A standing finding stays cleared. Every other kind clears only when its cause
  is settled. Only the decision clears the alert on an unhandled corporate action.
- How the kinds rank. Proposed: a fixed kind order, failed runs first and findings
  last, with the corporate action decision ahead of the findings; within a kind, what
  rests on the alert, then a natural key. The home view is a digest of the top rows of
  each kind with a count; a kind's full list pages by keyset cursor, as the other admin
  lists do.
- Whether the per-surface lists stay. Proposed: they stay. The runs page is the record
  of a run; the alerts page is the worklist.
- Whether the alerts read is one RPC or two. Proposed: a digest RPC for the home view
  and the nav count, and a list RPC that requires a kind and pages.
- What counts and dates each kind shows, and which have none. Proposed: each subject
  carries its own counts and dates, and the envelope holds only the kind.
- What a corporate action decision records and what keys it. Proposed: an enum column
  on the action row, where unspecified means undecided, which the refetch pairing
  ignores. A refetch that restates the ex-date or ratio deletes the row and its
  decision; the restated action is a new action and raises a new alert. The effective
  restates-shares is the decision where one exists, otherwise the stored handled.
  Holdings are restated on read from the calendar, so a changed decision takes effect
  at once.
- Whether a decision records restates-shares alone or a type that implies it.
