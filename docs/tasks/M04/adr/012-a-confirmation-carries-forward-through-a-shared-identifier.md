# A confirmation carries forward through a shared identifier

A confirmation associates the keys that exist when it is made. Each monthly statement
mints a new key for the same holding, and a re-upload of a period mints new keys for every
line in it, so a confirmation that reached only the keys of the moment would be asked for
again every month. Resolution therefore carries a confirmation forward. Before any
datasource is asked, a key that the lookup left unassociated is read against the user's
own keys whose arbiter is user. Where it shares a joining identifier with them, in the
sense the group package gives the term, and they all name one instrument, the key takes
that association: the same instrument, listing, identifier and validity, with the arbiter
user. Where they name more than one instrument, the key keeps its lack of an association,
a contradiction finding names the two instruments, and the key goes to the datasources.

The arbiter is user even though the user never saw the new key, because the user
arbitrated the holding and the new key states what the chosen key stated. A bare ticker
is not a joining identifier, so a confirmation reaches a later key through its broker
description or a GUID.

The deferred pin is an annotation that overrides an association a datasource made. This
rule applies to a key that has no association. It reads the keys that resolution writes.
